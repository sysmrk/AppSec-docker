# Runtime registry source priority

In Control Center > Settings > Registries > Trusted image pull sources, add endpoints with aliases and ascending numeric priority. Endpoints may include a repository prefix, e.g. harbor.example.org/dockerhub or hub.hamdocker.ir. Host-only entries continue working. Configure explicitly approved upstreams such as ghcr.io only if their direct access is allowed. Known explicit upstreams ghcr.io, docker.io, mcr.microsoft.com and quay.io are matched only to their own image origin; other endpoints are treated as repository mirrors.

The resolver tries each source in order, including alternative helper paths within one source, and stops at the first successful Docker pull. Unqualified Docker Hub official image names are normalized to library/name. Explicit non-Hub paths are preserved. A failed source is logged with a bounded diagnostic. If sources exist but are disabled or unsuitable, the resolver fails rather than adding the original registry. With no configured rows, legacy direct mode remains unless APPSEC_REQUIRE_IMAGE_SOURCES=true is supplied to runtime services.

## Copa and BuildKit

Copa v0.14.1 supports EXPERIMENTAL_BUILDKIT_SOURCE_POLICY. After initial scan approval, AppSec reads Trivy OS metadata, resolves the known Debian/Ubuntu/RPM helper candidates through the same source priority, and creates a temporary per-job BuildKit source policy. The policy converts the known Copa helper identifiers (including the ordinary upstream fallback) to the selected approved reference and denies other LLB image sources. Alpine needs no helper. Unknown distributions or additional unmapped helpers fail closed; RPM chroot and SUSE mappings are not exhaustive. The previously scanned target must still belong to an enabled endpoint. The policy file is removed after the patch invocation. No manual helper tag/push is required for this route.

This policy is experimental upstream functionality, not a network firewall. Test it with the installed Copa and BuildKit versions. BuildKit daemon registry configuration, Docker daemon mirrors, auth realms, registry redirects, and arbitrary package-manager traffic are separate from source policy. Existing local buildkit-local.toml overrides pointing at localhost:8081 should be reviewed; remove stale mirror mappings if using direct approved endpoints. Apply outbound allowlists for strict network enforcement. A successful Docker pull does not prove that BuildKit can contact the same selected endpoint. Source policy does not implement BuildKit-side fallback after a Docker pull succeeds. Digest-pinned references are preferable; mirror tag equivalence is not guaranteed.

## Scanner tools and OCI artifacts

Trivy and Gitleaks runtime images use the same ordered resolver when a policy exists. Trivy scans use the local Docker image source and its tool image is run without implicit pull when configured. Trivy vulnerability and Java DB repository lists are generated from the approved endpoints in source order; these are OCI artifacts, not runnable Docker images. The vulnerability DB is explicitly prepared one approved endpoint at a time, including fallback after HTTP 403/404. Trivy may reuse a fresh cache. After preparation, scans skip a second vulnerability DB update. Java DB uses the ordered native repository list by default; set APPSEC_PREFETCH_JAVA_DB=true for explicit sequential Java DB preparation (large download), after which the scan skips Java DB updates too. Ensure at least one configured endpoint actually mirrors these artifacts, using the appropriate repository prefix. When no policy is configured, the existing TRIVY_IMAGE, TRIVY_DB_REPOSITORY, TRIVY_JAVA_DB_REPOSITORY, GITLEAKS_IMAGE settings continue to work.

Bootstrap images (Postgres, MinIO, BuildKit, Nginx, Metabase, runner base), the standalone maintenance updater, and APT/APK/RPM repositories are separate. They cannot rely on a database-backed policy before startup. Configure them in deployment settings or Compose overrides, and use an egress allowlist in production. Package sources and signing keys must already be valid in target/tooling images; AppSec does not rewrite package sources or disable signature checks.

## Upgrade and validation

Stop the platform, retain .env and Compose overrides, back up the DB and evidence, fetch main, then run ./appsec start. Test with a known Debian image and at least two approved mirrors (first unavailable, second available), review IMAGE_SOURCE_TRY/IMAGE_SOURCE_FAILED/IMAGE_SOURCE_SELECTED and COPA_SOURCE_POLICY in worker logs. Validate the actual BuildKit network path, then confirm a successful post-patch scan. Disable all sources and verify a new scan fails without attempting a direct upstream. Preserve failures as audit evidence. No registry publication occurs before separate approval.

Set APPSEC_REQUIRE_IMAGE_SOURCES=true in .env and recreate runtime containers to fail closed even when the last entry is removed. Do not enable this until the configured sources cover target images, tool images, and scanner DBs. Bootstrap images are individually configurable with POSTGRES_IMAGE, MINIO_IMAGE, MINIO_MC_IMAGE, NGINX_IMAGE, BUILDKIT_IMAGE, METABASE_IMAGE, RUNNER_BASE_IMAGE and DOCKER_CLI_IMAGE. These settings are applied before DB startup; they are explicit references, not automatic fallback. APPSEC_PIP_INDEX_URL configures the runner build package index without changing target package manager repositories. Do not put credentials in build args.

APPSEC_DEBIAN_MIRROR supplies the runner build's Debian archive base (for example https://mirrors.tuna.tsinghua.edu.cn). It preserves APT signature verification and does not modify target/tooling images. After an upgrade with local Dockerfile modifications, save them first; use the new environment setting instead of copying an outdated Dockerfile over the tracked file.

Tool release selection is documented in [Tool updates](tool-updates.md). A managed scanner version must match the version returned by the selected mirror. Trivy timeouts and cache troubleshooting are documented in [Operations](operations-runbook.md).
